# Функциональный сценарий

## 1. Исходное состояние

Перед пользователем находится пустая директория задания на расчет.

В эту директорию пользователь должен поместить файл `calculation.toml` с конфигурацией одного разового запуска конкретного расчета.

На этом этапе:

- расчет еще не подготовлен;
- исполняемые файлы еще не загружены;
- входные файлы еще не загружены;
- отдельное рабочее окружение расчета еще не создано;
- manifest/lock-файлы еще не созданы;
- запуск расчета еще не выполнялся.

Функциональная ответственность:

- файл `calculation.toml` описывает намерение пользователя: какой расчет нужно подготовить и выполнить.

Статус расчета:

- `ConfigDraft`

## 2. Источник исполняемого файла

Первым содержательным элементом `calculation.toml` является источник исполняемого файла расчетного кода.

Исполняемый файл нельзя рассматривать отдельно от правил работы с его файлами. Для конкретного расчетного кода должны быть известны связанные с ним наборы правил:

- какие входные файлы он ожидает;
- как входные файлы должны быть размещены в рабочем окружении;
- какие файлы после запуска считаются результатами;
- какие файлы являются служебными, временными или логами.

Функциональная ответственность:

- пользователь указывает источник расчетного кода;
- пользователь указывает или выбирает профиль правил, совместимый с этим расчетным кодом;
- программа должна понимать, какие правила входов и выходов применяются именно к выбранному исполняемому файлу.

## 3. Каталог расчетных кодов

Каталог расчетных кодов является опциональным удобством автоматического режима.

Пользователь может работать двумя способами:

- выбрать расчетный код и правила из каталога расчетных кодов;
- напрямую указать в `calculation.toml` путь до директории с расчетным кодом и путь до файла правил.

В автоматическом режиме пользователь не обязан вручную описывать исполняемый файл и все связанные правила.

Пользователь указывает в `calculation.toml` путь к каталогу расчетных кодов.

Программа должна:

- загрузить каталог расчетных кодов;
- показать пользователю доступные расчетные коды;
- показать доступные версии выбранного расчетного кода;
- после выбора версии показать наборы правил, применимые к этой версии;
- явно показывать статус каждого набора правил.

Каталог расчетных кодов функционально хранит три группы данных.

### 3.1. Расчетный код

Для каждого расчетного кода каталог хранит:

- название расчетного кода;
- версию расчетного кода;
- путь до директории с кодом, которую нужно выгрузить;
- относительный путь до главного исполняемого файла внутри этой директории;
- варианты команд запуска с комментариями.

### 3.2. Файл с наборами правил

Для каждого файла правил каталог хранит:

- id набора правил;
- название файла правил;
- путь, откуда этот файл правил нужно выгрузить.

### 3.3. Применение наборов правил

Каталог хранит связь между расчетным кодом, его версией и набором правил:

- название расчетного кода;
- версия расчетного кода;
- id набора правил;
- статус набора правил: `stable`, `experimental` или `deprecated`.

Смысл статуса:

- `stable` - набор правил проверен и рекомендуется для обычного автоматического запуска;
- `experimental` - набор правил находится в проверке и должен быть явно помечен для пользователя;
- `deprecated` - набор правил больше не рекомендуется к использованию, но может быть доступен для воспроизведения старых расчетов.

## 4. Выбор расчетного кода из каталога

После загрузки каталога пользователь выбирает:

- расчетный код;
- версию расчетного кода;
- подходящий набор правил;
- команды запуска остаются в каталоге расчетных кодов и выбираются позже, непосредственно перед запуском.

После выбора программа должна сформировать в текущем расчете конкретную привязку к выбранному коду:

- откуда будет выгружена директория расчетного кода;
- какой файл внутри этой директории является главным исполняемым файлом;
- какой файл правил будет использован;
- какой статус имеет выбранный набор правил;
- где в каталоге находятся варианты команд запуска для выбранного расчетного кода.

На этом этапе программа еще не обязана запускать расчет.

Функциональная ответственность:

- выбор пользователя превращается в конкретное описание расчетного кода для данного запуска;
- программа должна показать пользователю итоговый выбор до подготовки рабочего окружения;
- если выбран `experimental` или `deprecated` набор правил, пользователь должен увидеть явное предупреждение.

## 5. Формирование `calculation.lock.toml`

После выбора расчетного кода и набора правил программа начинает формировать `calculation.lock.toml`.

`calculation.toml` описывает исходное пользовательское намерение.

`calculation.lock.toml` описывает конкретизированную конфигурацию, по которой будет собираться окружение расчета.

Если пользователь вручную полностью заполнил `calculation.toml`, программа должна:

- скопировать конкретизированные данные в `calculation.lock.toml`.

Если пользователь работает через каталог расчетных кодов или вспомогательные инструменты, они не должны переписывать исходный `calculation.toml`.

Вместо этого они должны постепенно наполнять `calculation.lock.toml`.

Валидируется именно `calculation.lock.toml`.

Это правило действует независимо от того, как lock-файл был получен:

- скопирован из полностью заполненного `calculation.toml`;
- собран программно через каталог расчетных кодов;
- отредактирован пользователем вручную.

Функциональная ответственность:

- `calculation.toml` остается пользовательским исходным описанием;
- `calculation.lock.toml` становится рабочей конфигурацией подготовки расчета;
- сборка окружения должна выполняться именно по `calculation.lock.toml`;
- lock-файл должен фиксировать выбранный расчетный код, версию, источник кода, главный исполняемый файл, файл правил и статус правил;
- команды запуска не являются частью сборки окружения и остаются в каталоге расчетных кодов до этапа запуска.

`calculation.lock.toml` и manifest - разные файлы с разной ответственностью:

- `calculation.lock.toml` описывает только сборку окружения расчета;
- manifest хранит полную фактическую информацию о подготовке, запуске, файлах, хэшах, логах и результатах.

## 6. Источники входных файлов

После выбора расчетного кода и файла правил у программы еще нет информации о конкретных исходных файлах для расчета.

Возможны три функциональных сценария получения входных файлов.

### 6.1. Пользователь явно указывает входные источники

Пользователь сам знает, какие файлы нужны расчету, и указывает источники входных файлов напрямую.

Для каждого источника пользователь указывает:

- путь или адрес источника;
- тип источника;
- набор правил, который нужно применить к файлам этого источника;
- при необходимости - версию источника.

Этот сценарий является текущим рассматриваемым вариантом.

Дальнейшее функциональное обсуждение входных файлов ведется только для этого сценария.

### 6.2. Входы берутся из предыдущего расчета

Входные файлы текущего расчета могут быть результатами предыдущего расчета в цепочке.

Этот сценарий закреплен на будущее.

Сейчас он не рассматривается детально.

На текущем этапе нужно только не принимать решений, которые помешают позже использовать результат одного расчета как вход другого.

### 6.3. Пользователь выбирает входные наборы из каталога файловых наборов

Может существовать отдельный каталог наборов входных файлов.

Каталог хранит:

- объект или набор файлов;
- путь или адрес, откуда этот набор можно выгрузить;
- правила или рекомендуемые правила применения;
- список расчетных кодов и версий, с которыми этот набор совместим;
- статус совместимости.

Этот сценарий требует дальнейшего отдельного рассмотрения.

Сейчас он не входит в текущий разбор.

Функциональная ответственность:

- расчетный код и файл правил определяют, какие типы входов ожидаются;
- пользователь или каталог входных наборов определяет, какие конкретные файлы будут использованы;
- выбранные входные источники должны попадать в `calculation.lock.toml`, потому что они участвуют в сборке окружения.

## 7. Добавление входных источников в `calculation.lock.toml`

В текущем рассматриваемом сценарии пользователь вручную указывает один или несколько входных источников.

Для каждого входного источника пользователь указывает:

- имя источника;
- путь или адрес источника;
- тип источника;
- версию, если источник версионируемый;
- имя набора правил, который нужно применить к этому источнику.

Эти данные переносятся в `calculation.lock.toml`.

На момент добавления входных источников файл правил может быть еще не выгружен.

Поэтому программа не обязана сразу проверять, существует ли указанный пользователем набор правил.

Проверка соответствия выполняется позже, на этапе валидации `calculation.lock.toml`.

В текущем ручном сценарии ранняя проверка существования набора правил не требуется.

В будущем вспомогательный скрипт или GUI могут выполнять такую проверку сразу после выбора расчетного кода и загрузки файла правил.

Функциональная ответственность:

- пользователь может описать все входные источники заранее;
- программа сохраняет эти источники в lock-файл;
- валидация lock-файла должна проверить, что указанные наборы правил действительно существуют в выбранном файле правил;
- если набор правил не найден, сборка окружения не должна начинаться.

## 8. Валидация `calculation.lock.toml` перед сборкой окружения

Перед сборкой окружения программа должна провалидировать `calculation.lock.toml`.

Сборка окружения не должна начинаться, пока lock-файл не прошел валидацию.

Цель валидации:

- проверить, что все необходимые данные для сборки указаны;
- проверить доступность расчетного кода;
- проверить доступность файла правил;
- проверить доступность входных источников;
- проверить корректность и применимость правил;
- заранее обнаружить конфликты путей назначения;
- построить план сборки окружения.

### 8.1. Проверка структуры lock-файла

Программа проверяет, что в `calculation.lock.toml` указаны:

- источник директории расчетного кода;
- относительный путь до главного исполняемого файла;
- источник файла правил;
- входные источники;
- имя набора правил для каждого входного источника.

Если обязательных данных не хватает, сборка окружения не начинается.

### 8.2. Проверка расчетного кода

Программа проверяет:

- источник директории расчетного кода доступен;
- указанная версия существует, если источник версионируемый;
- указанный путь внутри источника существует;
- главный исполняемый файл существует внутри директории расчетного кода по указанному относительному пути.

### 8.3. Проверка файла правил

Файл правил всегда выгружается как текст.

На этапе валидации программа должна:

- проверить, что источник файла правил доступен;
- прочитать файл правил как текст;
- не сохранять файл правил локально до завершения валидации.

Локально файл правил сохраняется только после успешной валидации lock-файла и правил.

### 8.4. Проверка читаемости входных источников

Для каждого входного источника программа проверяет:

- источник доступен;
- указанная версия существует, если источник версионируемый;
- указанный путь внутри источника существует;
- список файлов источника можно получить;
- файлы доступны для чтения.

### 8.5. Валидация правил

После проверки читаемости входных источников программа валидирует правила.

Программа должна проверить:

- файл правил имеет корректный формат;
- все наборы правил, указанные в `calculation.lock.toml`, существуют в файле правил;
- регулярные выражения в правилах корректны;
- шаблоны целевых путей корректны;
- используемые маркеры поддерживаются.

Если хотя бы один указанный набор правил не найден или содержит ошибку, сборка окружения не начинается.

### 8.6. Проверка применимости правил

После валидации правил программа применяет правила к спискам файлов источников в режиме preview.

Программа должна проверить:

- какие файлы будут взяты из каждого источника;
- куда каждый файл будет помещен в рабочем окружении;
- нет ли конфликтов путей назначения;
- не остаются ли непокрытые файлы при строгом режиме правил;
- целевые пути не выходят за пределы рабочего окружения;
- служебные файлы программы не будут перезаписаны.

### 8.7. План сборки окружения

Результатом успешной валидации должен быть план сборки окружения.

План сборки описывает:

- какие файлы будут взяты;
- из какого источника будет взят каждый файл;
- куда будет помещен каждый файл;
- какое правило применилось;
- к какому входному источнику или расчетному коду относится файл.

Только после построения успешного плана сборки программа может переходить к физической сборке окружения.

## 9. Сборка окружения расчета

Сборка окружения выполняется только после успешной валидации `calculation.lock.toml` и построения плана сборки.

Сборка должна выполняться по плану сборки, а не напрямую по lock-файлу.

`calculation.lock.toml` описывает намерение сборки, а план сборки содержит уже проверенную конкретику:

- какой файл взять;
- из какого источника взять;
- куда положить;
- какое правило применилось.

### 9.1. Разделение директории задания и рабочего окружения

Служебные файлы программы не должны находиться в рабочем окружении расчета.

Нужно разделять:

- директорию задания, где лежат пользовательские конфиги, lock, manifest, файл правил, планы сборки, снимки и служебные отчеты;
- отдельную директорию рабочего окружения, куда выгружаются только файлы расчетного кода и входные файлы.

Рабочее окружение должно быть чистым от конфигов программы, manifest, файла правил и других служебных файлов.

Так проще:

- выгружать результаты;
- отслеживать изменения файлов расчета;
- отделять файлы пользователя от файлов программы;
- не смешивать служебные данные с расчетными файлами.

### 9.2. Проверка состояния директорий

Перед первой сборкой программа проверяет:

- директория задания содержит допустимые конфигурационные и служебные файлы;
- директория рабочего окружения отсутствует или пуста;
- в рабочем окружении нет неизвестных файлов от предыдущих запусков.

Если в рабочем окружении есть неизвестные файлы, программа не должна молча продолжать сборку.

### 9.3. Создание служебной области

Программа создает служебную область в директории задания, а не внутри рабочего окружения расчета.

Служебная область нужна для хранения:

- локальной копии файла правил;
- плана сборки;
- снимков рабочего окружения;
- будущего manifest;
- логов и служебных отчетов;
- замороженных pre-run копий входных файлов;
- runtime status во время выполнения расчета.

Служебные файлы должны быть физически отделены от файлов самого расчета.

Служебная область обязательна для работы программы и должна находиться вне рабочего окружения расчета.

### 9.4. Сохранение файла правил

Файл правил сохраняется локально только после успешной валидации.

Сохраняется именно тот текст файла правил, который был прочитан и провалидирован на этапе валидации.

Это нужно, чтобы последующая сборка и будущий manifest ссылались на конкретный использованный файл правил.

Файл правил сохраняется в служебной области, а не в рабочем окружении расчета.

### 9.5. Выполнение плана сборки

Программа последовательно выполняет план сборки:

- выгружает файлы расчетного кода;
- выгружает входные файлы;
- помещает каждый файл в целевой путь рабочего окружения;
- фиксирует, какой исходный файл стал каким локальным файлом.

Во время сборки программа не должна:

- выходить за пределы рабочего окружения при размещении расчетных файлов;
- перезаписывать служебные файлы;
- перезаписывать уже скопированные файлы;
- создавать конфликты между файлами расчетного кода и входными файлами.

Если план сборки прошел проверку конфликтов, порядок копирования не должен менять итоговый результат.

### 9.6. Проверка результата сборки

После копирования программа проверяет уже собранное рабочее окружение.

Минимально нужно проверить:

- главный исполняемый файл действительно находится в рабочем окружении по ожидаемому пути;
- все файлы из плана сборки скопированы;
- служебные файлы программы не повреждены.

### 9.7. Отчет о сборке

После успешной сборки программа формирует отчет о сборке.

Отчет должен содержать:

- какие файлы были скопированы;
- откуда был взят каждый файл;
- куда был помещен каждый файл;
- какое правило применилось;
- к какому источнику относится файл.

Отчет о сборке является частью будущей полной информации о расчете, но еще не заменяет manifest.

### 9.8. Снимок рабочего окружения после сборки

Сразу после успешной сборки программа должна сохранить снимок рабочего окружения.

Снимок фиксирует чистое состояние расчета после сборки и до запуска.

Для каждого файла в снимке нужно хранить:

- относительный путь;
- хэш файла;
- размер файла;
- роль файла;
- источник файла, если он известен.

Этот снимок нужен, чтобы обнаружить ручные изменения файлов между сборкой и запуском.

Перед запуском программа сделает новый снимок и сравнит его со снимком после сборки.

Если пользователь изменит, добавит или удалит файлы после сборки, программа должна это обнаружить.

### 9.9. Состояние после сборки

После успешной сборки, отчета и снимка рабочего окружения расчет переходит в состояние `Prepared`.

Состояние `Prepared` означает:

- окружение собрано;
- исходное состояние рабочего окружения зафиксировано;
- расчет еще не запускался;
- перед запуском потребуется проверить, не изменил ли пользователь файлы вручную.

## 10. Действия перед запуском расчета

В состоянии `Prepared` пользователь имеет право вручную изменить файлы расчета.

Перед запуском программа должна зафиксировать фактическое состояние файлов рабочего окружения, с которыми расчет будет стартовать.

Для этого программа делает снимок рабочего окружения перед запуском:

- `pre_run_snapshot`.

Затем программа сравнивает:

- снимок после сборки;
- снимок перед запуском.

Цель сравнения:

- обнаружить измененные файлы;
- обнаружить добавленные файлы;
- обнаружить удаленные файлы;
- классифицировать изменения по ролям файлов;
- определить, можно ли запускать расчет;
- определить, какие входные файлы нужно сохранить отдельно для будущей воспроизводимости.

### 10.1. Каталог расчетных кодов не блокирует запуск и публикацию

Каталог расчетных кодов используется как помощник выбора.

Он не является источником воспроизводимости после формирования `calculation.lock.toml`.

Изменение каталога расчетных кодов не должно блокировать:

- запуск расчета;
- выгрузку результатов;
- публикацию в версионируемый источник.

Для воспроизводимости важны:

- `calculation.lock.toml`;
- локально сохраненный файл правил;
- собранные файлы расчетного кода;
- снимки рабочего окружения;
- фактически выбранная команда запуска;
- manifest.

### 10.2. Блокирующие изменения перед запуском

Для публикации результата в версионируемый источник критичными считаются изменения:

- `calculation.lock.toml`;
- локально сохраненного файла правил;
- файлов расчетного кода;
- служебных файлов сборки и снимков.

Если такие изменения обнаружены, результат нельзя выгружать в версионируемый источник как воспроизводимый.

Изменение `calculation.toml` после формирования lock-файла не блокирует запуск или публикацию, но программа должна сообщить пользователю о таком изменении перед запуском.

Локальный запуск при таких изменениях может быть разрешен, но manifest должен явно зафиксировать нарушение воспроизводимости.

### 10.3. Изменения входных файлов

Изменение входных файлов после сборки является допустимым пользовательским сценарием.

Такие изменения не должны автоматически запрещать запуск.

Но перед запуском программа должна сохранить именно ту версию входных файлов, которая будет использована расчетом.

Эта версия фиксируется по `pre_run_snapshot`.

Это необходимо, потому что после запуска расчетный код может дополнительно изменить входные файлы, и восстановить их стартовое состояние будет невозможно.

### 10.4. Замороженные входные файлы

Если входной файл был изменен пользователем после сборки, программа должна до запуска сохранить его pre-run версию как замороженный входной файл.

Если входной файл пришел из неверсионируемого источника и результат планируется публиковать в версионируемый источник, программа также должна сохранить его pre-run версию как замороженный входной файл.

Замороженные входные файлы нужны для дальнейшей публикации и воспроизводимости расчета.

### 10.5. Ссылки на входные файлы в manifest

Manifest должен ссылаться на фактическую версию входного файла, которая использовалась на старте расчета.

Правила ссылок:

- если файл пришел из версионируемого источника и не был изменен, manifest ссылается на исходный версионируемый источник;
- если файл был изменен пользователем, manifest ссылается на замороженную pre-run версию или на ее опубликованную версию после выгрузки;
- если файл пришел из неверсионируемого источника, manifest ссылается на замороженную pre-run версию или на ее опубликованную версию после выгрузки;
- если файл относится к расчетному коду и не был изменен, manifest ссылается на источник расчетного кода из lock.

Manifest должен описывать не текущее состояние файла после запуска, а конкретную версию файла, с которой расчет стартовал.

## 11. Политики публикации результата

После запуска результат может быть опубликован в версионируемый или неверсионируемый источник.

Публикация должна учитывать происхождение и изменения входных файлов.

### 11.1. Публикация при неизмененных версионируемых входах

Если все входные файлы пришли из версионируемых источников и не были изменены пользователем, результат можно публиковать в версионируемый источник.

Manifest должен ссылаться на исходные версии входных файлов.

### 11.2. Публикация при измененных входных файлах

Если входные файлы были изменены пользователем до запуска, при публикации в версионируемый источник программа должна предложить опубликовать замороженные pre-run версии этих входных файлов.

Публиковать нужно именно pre-run версии, а не текущее состояние файлов после завершения расчета.

После публикации manifest должен ссылаться на опубликованные версии измененных входных файлов.

### 11.3. Публикация при неверсионируемых входных источниках

Если входные файлы пришли из неверсионируемых источников, а результат нужно сохранить в версионируемый источник, программа должна сначала опубликовать pre-run версии таких входных файлов в отведенное место версионируемого источника.

После этого manifest должен ссылаться уже на опубликованные версионируемые копии входных файлов.

Только после публикации входных файлов можно публиковать результаты расчета.

### 11.4. Публикация в неверсионируемый источник

Если результат публикуется в неверсионируемый источник, измененные или неверсионируемые входные файлы сохраняются рядом с результатом в отдельной области.

Manifest должен ссылаться на эти сохраненные копии.

Неизмененные файлы из версионируемых источников повторно сохранять не требуется.

### 11.5. Запрет публикации как воспроизводимого результата

Результат нельзя публиковать как воспроизводимый в версионируемый источник, если перед запуском были изменены:

- lock-файл;
- файл правил;
- файлы расчетного кода;
- служебные снимки или план сборки.

В таких случаях возможен только локальный запуск или специальный режим публикации с явной пометкой о нарушенной воспроизводимости, если такой режим будет разрешен отдельно.

## 12. Запуск расчета

На текущем этапе рассматривается только запуск расчетного кода через консоль.

После подготовки окружения пользователь выбирает пресет запуска.

Пресеты запуска могут храниться в каталоге расчетных кодов и быть связаны с конкретным расчетным кодом и его версией.

### 12.1. Пресет запуска

Пресет запуска должен содержать:

- название пресета;
- описание для пользователя;
- команду запуска с параметрами;
- параметры команды, которые нужно запросить у пользователя перед запуском;
- набор переменных среды;
- опциональный stdin script для простого диалогового режима.

Команда запуска выбирается непосредственно перед запуском и не является частью сборки окружения.

Фактически выбранная команда запуска должна быть зафиксирована в manifest.

Пресет может хранить не только готовую команду, но и шаблон команды с параметрами.

Для параметра команды можно указать:

- имя параметра;
- обязательность;
- значение по умолчанию;
- подсказку для пользователя;
- допустимые значения, если они известны.

Перед запуском программа должна:

- запросить у пользователя значения недостающих параметров;
- применить значения по умолчанию;
- собрать фактическую команду запуска;
- зафиксировать в manifest только уже собранную фактическую команду.

В manifest не нужно сохранять исходный шаблон команды как источник запуска. Источником фактического запуска является уже собранная команда.

При проектировании подстановки параметров нужно учитывать риск командных инъекций.

В первой версии достаточно зафиксировать это как обязательное требование безопасности для реализации, даже если защита будет минимальной.

### 12.2. Переменные среды

Программа должна контролировать переменные среды, с которыми запускается расчет.

Переменные среды могут приходить из выбранного пресета запуска.

Перед запуском программа должна зафиксировать фактический набор переменных среды, влияющий на процесс.

Этот набор должен попасть в manifest.

Пресет запуска может содержать не только фиксированные переменные среды, но и переменные, значения которых нужно запросить у пользователя перед запуском.

Для запрашиваемой переменной среды в пресете можно указать:

- имя переменной;
- обязательность;
- значение по умолчанию;
- подсказку для пользователя;
- признак секретного значения.

Перед запуском программа должна:

- прочитать требования к переменным среды из пресета;
- взять фиксированные значения из пресета;
- запросить у пользователя недостающие обязательные значения;
- применить значения по умолчанию, если они заданы;
- не сохранять секретные значения в manifest и логи в открытом виде.

Для секретных переменных manifest может фиксировать только факт, что значение было предоставлено.

### 12.3. Простой stdin script

Для первой версии достаточно поддержать простой режим stdin script.

В этом режиме программа передает расчетному процессу заранее заданную последовательность строк ввода.

Этот режим подходит для расчетных программ, у которых диалоговый интерфейс стабилен и всегда ожидает ответы в одном порядке.

### 12.4. Логирование взаимодействия с процессом

Во время запуска программа должна логировать:

- stdout расчетного процесса;
- stderr расчетного процесса;
- stdin, который был передан процессу;
- выбранный пресет запуска;
- время старта и завершения;
- код возврата процесса.

Логи запуска должны быть сохранены вне рабочего окружения расчета, в служебной области задания.

### 12.5. Интерактивный режим как будущее расширение

Более сложный режим взаимодействия с расчетной программой, где программа ожидает конкретный текст в stdout и только после этого передает нужный ввод, закрепляется как будущее расширение.

В первой версии такой prompt-response режим не обязателен.

### 12.6. Ручной диалоговый режим

Если расчетная программа требует диалогового ввода, но заранее подготовленного stdin script нет, программа должна поддерживать ручной диалоговый режим.

В этом режиме программа:

- показывает пользователю stdout/stderr расчетного процесса;
- принимает ввод пользователя;
- передает ввод пользователя в stdin расчетного процесса;
- записывает stdout, stderr и stdin в лог взаимодействия.

Ручной диалоговый режим не использует prompt-response логику.

Он нужен, чтобы пользователь мог выполнить расчет с неизвестным заранее диалогом, а программа могла сохранить фактическую историю взаимодействия.

## 13. Работа программы во время выполнения расчета

Расчет может выполняться долго: от нескольких минут до нескольких дней.

Во время выполнения программа не должна просто ожидать завершения процесса.

Она должна вести состояние запуска и сохранять наблюдаемую информацию.

### 13.1. Состояние `Running`

Сразу после успешного старта процесса расчет переходит в состояние `Running`.

На этом этапе фиксируются:

- время старта;
- фактическая команда запуска;
- фактические переменные среды;
- идентификатор процесса, если он доступен;
- выбранный пресет запуска.

### 13.2. Потоковое логирование

Во время выполнения программа должна постоянно сохранять:

- stdout расчетного процесса;
- stderr расчетного процесса;
- stdin, который был передан процессу.

Логи должны записываться вне рабочего окружения расчета, в служебной области директории задания.

Это нужно, чтобы:

- пользователь мог видеть прогресс;
- GUI или API могли показывать последние строки логов;
- при аварийном завершении уже записанные логи не потерялись;
- логи не попадали в снимки рабочего окружения как расчетные output-файлы.

### 13.3. Runtime status

Во время выполнения программа должна поддерживать временный статус текущего запуска.

Runtime status нужен для GUI и API.

Он может содержать:

- текущее состояние;
- время старта;
- время последнего обновления;
- размер логов;
- последнюю активность stdout/stderr;
- признак запрошенной остановки;
- timeout, если он задан.

Runtime status не заменяет manifest.

Manifest формируется после завершения расчета.

### 13.4. Остановка и timeout

Для долгих расчетов должна быть предусмотрена возможность остановки пользователем.

Минимально нужно различать:

- обычное завершение;
- завершение с ошибкой;
- остановку пользователем;
- принудительное завершение;
- завершение по timeout.

Если задан timeout, программа должна контролировать время выполнения и завершить расчет при превышении лимита.

### 13.5. Что не делается во время выполнения

Во время выполнения расчета программа не должна:

- пересчитывать хэши всех файлов рабочего окружения постоянно;
- пытаться окончательно определить output-файлы до завершения процесса;
- публиковать результаты;
- изменять `calculation.lock.toml`;
- считать runtime status финальным manifest.

Обязательные снимки рабочего окружения:

- перед запуском;
- после завершения.

Промежуточные снимки во время выполнения могут быть добавлены позже, но не обязательны для первой версии.

### 13.6. Фиксация завершения процесса

После завершения процесса программа фиксирует:

- время завершения;
- код возврата;
- причину завершения;
- итоговый статус запуска.

Возможные итоговые статусы:

- `Succeeded`;
- `Failed`;
- `Timeout`;
- `Cancelled`;
- `Killed`.

## 14. Действия сразу после завершения расчета

Сразу после завершения расчетного процесса программа должна зафиксировать последствия запуска.

После фиксации кода возврата и причины завершения программа делает снимок рабочего окружения после запуска:

- `post_run_snapshot`.

Снимок делается до публикации результатов, очистки, повторного запуска или ручного редактирования файлов.

`post_run_snapshot` охватывает только рабочее окружение расчета.

Служебные файлы задания, manifest, lock, файл правил и логи CalcChain в этот снимок не входят.

### 14.1. Сравнение снимков

После создания `post_run_snapshot` программа сравнивает:

- `pre_run_snapshot`;
- `post_run_snapshot`.

Результат сравнения:

- созданные файлы;
- измененные файлы;
- удаленные файлы;
- неизмененные файлы.

Это сравнение показывает, что расчетный код сделал с рабочим окружением.

### 14.2. Классификация изменений по умолчанию

Если специальные правила классификации результатов не заданы, программа считает результатами расчета все созданные и измененные файлы рабочего окружения.

Удаленные файлы результатами не считаются, но факт удаления должен быть зафиксирован.

Если входной файл был изменен во время запуска, он может одновременно быть:

- входом расчета на момент старта;
- результатом расчета после завершения.

Для входа manifest должен ссылаться на pre-run версию.

Для результата manifest должен ссылаться на post-run версию.

### 14.3. Частичная классификация изменений

В файле правил или настройках публикации могут быть заданы правила классификации:

- `output`;
- `log`;
- `temp`;
- `ignore`.

Могут быть заданы не все типы правил.

Например:

- если заданы `output` rules, файлы, не попавшие под правила, считаются `unknown`;
- если заданы только `log` rules, файлы, попавшие под них, считаются логами, а остальные созданные и измененные файлы по умолчанию считаются output;
- если заданы `temp` или `ignore` rules, попавшие под них файлы не считаются output.

Базовая политика:

- `output` - публикуется как результат расчета;
- `log` - считается логом расчета;
- `temp` - не публикуется как результат;
- `ignore` - игнорируется при публикации и предупреждениях;
- если среди заданных правил нет `output` rules, все неклассифицированные созданные и измененные файлы по умолчанию считаются output;
- если `output` rules заданы, все неклассифицированные созданные и измененные файлы считаются `unknown`.

### 14.4. Unknown и строгий режим

Файлы с классификацией `unknown` должны быть показаны пользователю.

В строгом режиме такие файлы могут блокировать публикацию до явного решения.

Для первой версии отсутствие правил классификации не является ошибкой.

### 14.5. Сохранение отчета после запуска

После классификации программа должна сохранить:

- `post_run_snapshot`;
- разницу между `pre_run_snapshot` и `post_run_snapshot`;
- отчет классификации файлов;
- предупреждения, если они есть.

Эти данные используются для формирования manifest и дальнейшей публикации результата.

## 15. Действия после формирования manifest

После завершения расчета, post-run snapshot и формирования manifest программа не должна сама решать, публиковать ли результат.

Она должна показать пользователю общую информацию:

- итоговый статус;
- код возврата;
- время выполнения;
- список найденных output-файлов;
- список log-файлов;
- предупреждения;
- оценку воспроизводимости.

Дальнейшее действие выбирает пользователь.

### 15.1. Если расчет завершился ошибкой

Если итоговый статус:

- `Failed`;
- `Timeout`;
- `Cancelled`;
- `Killed`;

то расчет не считается успешно завершенным.

Manifest должен формироваться и для неуспешного расчета.

Такой manifest нужен для диагностики и отчета об ошибке.

Пользователь должен иметь возможность:

- пересобрать рабочее окружение;
- изменить исходные настройки и пересобрать окружение;
- выгрузить manifest и логи как отчет об ошибке.

Отчет об ошибке не считается публикацией результата расчета.

Он нужен для диагностики и может включать:

- manifest;
- stdout/stderr/stdin логи;
- runtime status;
- предупреждения;
- снимки рабочего окружения, если они нужны для диагностики.

### 15.2. Если расчет завершился успешно

Если итоговый статус `Succeeded`, пользователь может:

- ничего не делать и самостоятельно работать с файлами;
- запустить публикацию результата через программу.

Ручное копирование пользователем не рассматривается как часть сценария публикации.

Дальнейший функциональный сценарий описывает только публикацию через программу.

## 16. Публикация результата

Публикация результата выполняется только по явному действию пользователя.

Пользователь выбирает, куда нужно выгрузить результаты расчета.

Целевой источник публикации может быть:

- локальной директорией;
- версионируемым источником;
- другим поддерживаемым хранилищем в будущем.

Целевой путь может быть:

- указан пользователем вручную;
- предложен через каталог расчетных кодов, если каталог знает рекомендуемое место для выходных данных выбранного расчетного кода.

### 16.1. Правила публикации

На текущем этапе один и тот же output rule set используется:

- для классификации файлов после запуска;
- для определения размещения файлов при публикации.

То есть правила output не только говорят, какие файлы являются результатами, но и могут задавать, куда эти файлы должны быть выгружены.

В будущем классификацию и правила публикации можно разделить, но сейчас они считаются одним набором.

### 16.2. Публикация по правилам

Если правила публикации указаны, программа должна применять их к output-файлам.

Правила определяют:

- какие output-файлы публикуются;
- куда каждый файл помещается в целевом источнике.

Перед публикацией программа должна проверить:

- нет ли конфликтов целевых путей;
- целевые пути не выходят за разрешенную область публикации;
- все обязательные output-файлы покрыты правилами, если включен строгий режим;
- файлы `temp` и `ignore` не публикуются как результат.

### 16.3. Публикация без правил

Если правила публикации не указаны, output-файлы копируются как есть.

По умолчанию нужно сохранять относительные пути output-файлов из рабочего окружения.

### 16.4. План публикации

Перед фактической публикацией программа должна построить план публикации.

План публикации показывает:

- какие output-файлы будут опубликованы;
- куда будет помещен каждый output-файл;
- какие замороженные входные файлы нужно опубликовать перед результатами;
- куда будут помещены замороженные входные файлы;
- куда будет опубликован manifest;
- есть ли блокирующие причины.

Публикация не должна начинаться, пока план публикации не построен и не проверен.

### 16.5. Публикация при необходимости замороженных входов

Если результат публикуется в версионируемый источник и расчет использовал:

- входные файлы, измененные пользователем перед запуском;
- входные файлы из неверсионируемых источников;

то программа должна сначала опубликовать pre-run версии таких входных файлов в отведенное место целевого источника.

После этого manifest должен ссылаться на опубликованные версии этих входных файлов.

Только после этого публикуются output-файлы.

Политика выбора места для публикации замороженных входных файлов требует отдельного обсуждения.

На текущем этапе фиксируется только требование: если такие файлы нужны для воспроизводимости, они должны быть опубликованы до публикации manifest.

### 16.6. Завершение публикации

Manifest публикуется в строго определенное место внутри целевого источника.

Поэтому manifest не обязан хранить ссылку на собственную опубликованную копию.

Порядок публикации:

1. Опубликовать все необходимые файлы: замороженные входные файлы, если они нужны, и output-файлы.
2. Зафиксировать версии опубликованных файлов в manifest.
3. Опубликовать manifest в строго определенное место.

Manifest должен обязательно публиковаться вместе с результатами расчета.

Именно manifest объясняет, как результаты были получены и как расчет можно воспроизвести.

Публикация результата через программу не считается завершенной, если manifest не был опубликован.

Минимально нужно зафиксировать:

- целевой источник;
- опубликованные output-файлы;
- опубликованные замороженные входные файлы, если они были;
- версии публикации, если целевой источник версионируемый;
- сообщение публикации, если оно использовалось.

После успешной публикации расчет получает состояние `Published`.

## 17. Минимальный состав manifest

Manifest хранит минимально необходимую фактическую информацию о конкретном запуске расчета.

Он должен позволять понять:

- что было собрано;
- какие правила и к каким источникам применялись;
- с какими фактическими входами расчет стартовал;
- какой командой расчет был запущен;
- что процесс вернул;
- какие файлы стали результатами.

`calculation.lock.toml` остается рабочей конфигурацией сборки.

Manifest не должен зависеть от `calculation.toml` и каталога расчетных кодов.

### 17.1. Идентификация запуска

Manifest должен хранить:

- уникальный идентификатор запуска;
- версию схемы manifest;
- дату и время создания manifest;
- итоговый статус расчета;
- путь к директории задания;
- путь к рабочему окружению;
- пользователь, если эти данные доступны;
- имя хоста, если эти данные доступны.

### 17.2. Lock-файл

Manifest должен хранить:

- путь к `calculation.lock.toml`;
- хэш `calculation.lock.toml`.

Lock-файл является источником сборки окружения.

### 17.3. Файл правил

Manifest должен хранить:

- путь к локально сохраненному файлу правил;
- хэш локально сохраненного файла правил.

### 17.4. Применение правил к источникам

Manifest должен хранить не только факт использования наборов правил, но и то, к каким источникам эти наборы были применены.

Это частично повторяет lock-файл, но нужно для самодостаточности manifest.

Если с lock-файлом что-то случится, по manifest должно быть понятно, какие источники участвовали в расчете и какие правила применялись к каждому источнику.

Для каждого применения правила нужно хранить:

- роль применения: расчетный код, входной источник или классификация результатов;
- имя источника, если оно есть;
- тип источника;
- адрес или путь источника;
- путь внутри источника, если он есть;
- версия источника, если он версионируемый;
- id или имя набора правил;
- статус набора правил, если он известен.

### 17.5. Расчетный код

Manifest должен хранить:

- название расчетного кода;
- версию расчетного кода;
- источник расчетного кода;
- относительный путь до главного исполняемого файла в рабочем окружении;
- список файлов расчетного кода в рабочем окружении;
- хэш каждого файла расчетного кода после сборки.

### 17.6. Effective inputs

Manifest должен хранить фактические входные файлы, с которыми расчет стартовал.

Для каждого входного файла нужно хранить:

- имя входного источника;
- путь файла в рабочем окружении;
- источник фактической версии файла;
- хэш файла на момент запуска;
- признак, был ли файл изменен между сборкой и запуском.

Источник фактической версии файла определяется так:

- если файл пришел из версионируемого источника и не был изменен, указывается исходный версионируемый источник;
- если файл был изменен пользователем, указывается замороженная pre-run копия;
- если файл пришел из неверсионируемого источника, указывается замороженная pre-run копия.

### 17.7. Команда запуска

Manifest должен хранить:

- фактически собранную команду запуска;
- рабочую директорию процесса;
- фактические переменные среды;
- режим stdin: отсутствует, script или ручной диалоговый режим;
- пути к stdout, stderr и stdin log.

Для секретных переменных manifest не должен хранить открытое значение.

Для них допустимо хранить только факт, что значение было предоставлено.

### 17.8. Результат процесса

Manifest должен хранить:

- время старта;
- время завершения;
- код возврата;
- причину завершения;
- итоговый статус запуска.

Возможные итоговые статусы:

- `Succeeded`;
- `Failed`;
- `Timeout`;
- `Cancelled`;
- `Killed`.

### 17.9. Снимки рабочего окружения

Manifest должен ссылаться на обязательные снимки рабочего окружения:

- снимок после сборки;
- снимок перед запуском;
- снимок после завершения.

Для каждого снимка manifest должен хранить:

- путь к файлу снимка;
- хэш файла снимка.

### 17.10. Output-файлы

Manifest должен хранить итоговую классификацию файлов после запуска.

Для каждого файла, который участвует в результате post-run анализа, нужно хранить:

- путь в рабочем окружении;
- хэш post-run версии;
- классификацию: `output`, `log`, `temp`, `ignore` или `unknown`;
- признак, был ли файл создан или изменен;
- правило классификации, если оно применялось.

### 17.11. Воспроизводимость

Manifest должен хранить минимальную оценку воспроизводимости:

- можно ли считать расчет воспроизводимым;
- можно ли публиковать результат в версионируемый источник;
- блокирующие причины, если они есть;
- предупреждения, если они есть.

### 17.12. Что пока не входит в минимальный manifest

В минимальный manifest пока не включаются:

- `calculation.toml`;
- подробная информация о каталоге расчетных кодов;
- полная история выбора пользователя;
- подробный build report;
- подробная информация о публикации результата.

Эти разделы могут быть добавлены позже как опциональные.

## 18. Пересборка и повторный запуск

Для текущей версии повторный запуск одного расчета выполняется через пересборку рабочего окружения по `calculation.lock.toml`.

Базовый сценарий:

- пользователь запрашивает пересборку;
- текущее рабочее окружение удаляется или заменяется;
- программа заново валидирует lock;
- программа заново строит план сборки;
- программа заново собирает рабочее окружение;
- после сборки создается новый снимок рабочего окружения.

Повторный запуск поверх старого рабочего окружения без пересборки не является базовым сценарием.

На будущее можно улучшить пересборку:

- использовать кэш загруженных файлов, чтобы не обращаться к источникам повторно без необходимости;
- восстанавливать только файлы, которые были изменены относительно снимков;
- переиспользовать неизмененные части рабочего окружения.

Эти улучшения не входят в текущую версию.

## 19. Управление рабочим окружением

Для текущей версии программа должна уметь удалять рабочее окружение расчета.

Удаление рабочего окружения не должно удалять:

- `calculation.toml`;
- `calculation.lock.toml`;
- manifest;
- файл правил;
- снимки;
- логи;
- отчеты.

На будущее стоит добавить функции:

- очистка временных файлов;
- архивирование расчета;
- удаление старых логов;
- удаление старых снимков;
- сохранение только manifest и опубликованных результатов.

Эти функции относятся к будущим доработкам.

## 20. Dry-run и preview

Dry-run является обязательной функцией текущей версии.

Программа должна уметь показать пользователю, что будет сделано, без фактического изменения файлов и внешних источников.

Dry-run нужен минимум для:

- валидации `calculation.lock.toml`;
- построения плана сборки;
- preview сборки рабочего окружения;
- preview pre-run проверок;
- preview публикации результата.

Dry-run не должен:

- копировать файлы в рабочее окружение;
- публиковать результаты;
- изменять версионируемые источники;
- удалять рабочее окружение;
- изменять lock или manifest без явного режима сохранения.

## 21. Восстановление расчета по manifest

Восстановление расчета по manifest является обязательной функцией текущей версии.

Цель:

- по manifest создать новое рабочее окружение;
- восстановить расчетный код;
- восстановить фактические входные файлы;
- подготовить расчет к повторному запуску;
- проверить, что восстановленные файлы совпадают с хэшами из manifest.

При восстановлении нужно использовать именно фактические версии входов:

- исходные версионируемые источники, если входы не менялись;
- опубликованные или замороженные pre-run копии, если входы были изменены;
- опубликованные или замороженные pre-run копии, если исходные источники были неверсионируемыми.

Если нужные замороженные входные файлы недоступны, восстановление по manifest должно завершиться ошибкой.

Восстановление по manifest не должно зависеть от `calculation.toml` или каталога расчетных кодов.

## 22. Версии форматов

Форматы файлов должны быть версионированы.

Версия формата нужна минимум для:

- `calculation.lock.toml`;
- manifest;
- файла правил;
- каталога расчетных кодов.

Это нужно, чтобы будущие версии программы могли читать старые расчеты и корректно обрабатывать изменения схем.

## 23. Авторизация

В первой версии авторизация к источникам и целям публикации не рассматривается.

Работа с credentials, секретами доступа и пользовательскими правами требует отдельного обсуждения.

## 24. Портативность

Ядро проекта должно быть максимально кроссплатформенным и реализованным на Python.

Основная логика должна быть общей для Windows и Linux:

- работа с конфигурациями;
- валидация;
- сборка планов;
- snapshot;
- manifest;
- правила;
- публикация;
- восстановление.

Платформенно-зависимые части нужно по возможности изолировать.

К таким частям относятся:

- запуск консольных процессов;
- работа с интерактивным stdin/stdout;
- оболочки и отдельные пользовательские утилиты;
- особенности путей и кодировок.

Кодировки stdin/stdout/stderr нужно учитывать отдельно.

Предпочтительный внутренний формат текстовых данных программы - UTF-8.

При работе с расчетными программами может потребоваться перекодирование вывода и ввода в UTF-8, особенно на Windows.

В будущем для Windows и Linux могут понадобиться отдельные оболочки или вспомогательные утилиты.
